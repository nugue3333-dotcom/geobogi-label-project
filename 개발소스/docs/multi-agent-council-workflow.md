# 멀티 AI 에이전트 회의 워크플로

이 프로젝트의 기본 멀티 에이전트 방식은 Codex 앱 내부 서브에이전트를 사용하는 회의형 구조다. PowerShell에서 `codex.exe`를 다시 호출하는 방식은 Windows 샌드박스와 한글 경로 문제로 실제 수정이 누락될 수 있으므로 일반 작업에는 사용하지 않는다.

## 실행

Codex 앱 대화창에서 다음처럼 요청한다.

```text
Codex 앱 멀티에이전트로 [작업 설명] 진행해
```

메인 대화는 `lead-integrator` 역할을 맡고, 필요한 경우 앱 내부 서브에이전트를 띄워 아래 역할을 나눠 진행한다.

- `project-mapper`: 영향 파일, 실행 명령, 검증 명령, 위험 지점 확인
- `label-release-reviewer`: 고객용 실행파일, 출력 안전장치, dry-run, 배포 폴더 검토
- `feature-worker`: 지정된 좁은 파일 범위 구현
- `qa-release-verifier`: 테스트, 빌드, dry-run, 고객 실행 표면 검증

터미널 스크립트는 프롬프트/회의록 패키지를 남기는 레거시 보조 도구로만 사용한다.

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\start_agent_council.ps1 -Task "작업 설명"
```

`-Launch`는 Codex CLI를 터미널에서 중첩 실행하는 레거시 방식이며 기본적으로 차단된다. 명시적으로 승인된 진단에서만 `-Launch -AllowLegacyNestedLaunch`를 함께 지정할 수 있다. 실제 수정 작업은 Codex 앱 내부 서브에이전트를 사용한다.

## 라운드

1. 문제 진단: 파일 수정 없이 위험, 원인, 누락 정보를 찾는다.
2. 해결안 토론: 서로의 진단을 읽고 반박하거나 보완한다.
3. 합의안 구현: 쓰기 권한이 있는 에이전트만 맡은 범위에서 수정한다.
4. 검증과 출시 판단: 테스트, 빌드, 드라이런, 고객 실행 표면을 확인한다.

앱 내부 멀티에이전트에서는 메인 대화가 최종 회의록 역할을 한다. 터미널 레거시 스크립트를 썼을 때만 산출물이 `.agents/councils/yyyyMMdd_HHmmss/transcript.md`에 누적된다.

## 완료 기준

- 수정 파일, 고객용 실행폴더 반영 여부, 빌드 산출물 위치를 명확히 남긴다.
- printer side effect가 있는 작업은 기본 dry-run으로 검증한다.
- 고객용 EXE가 영향을 받으면 테스트, PyInstaller 빌드, `고객용_실행폴더` 복사, 해시 확인, 실제 EXE smoke 검증을 모두 수행한다.
- 고객 배포가 포함되면 새 `고객배포` 폴더 또는 명시된 고객 전달 폴더까지 반영 여부와 경로를 기록한다.
- `고객환경점검.exe --base-dir .\고객용_실행폴더`를 실행해 `out\customer_preflight_report.txt`와 `out\customer_support_package.zip` 생성 여부를 확인한다.
- dry-run 후 `print_queue.xlsx`, `print_log.xlsx`, `last_run.log`, `out\` 산출물을 확인하고 실패/누락을 최종 보고에 적는다.
- `--print`, `02_print_labels.cmd`, `run_label_job.ps1 -Mode Print`는 사용자의 명시 요청 없이는 실행하지 않는다.
- 실제 프린터 전송 성공과 실제 라벨 출력 성공을 같은 의미로 보고하지 않는다.
- 기본 템플릿은 의도적으로 비어 있어야 하며 `elements == []` 상태를 확인한다.
- `run_label_job.ps1` 또는 Excel 출력 흐름을 건드린 경우, 전체 행 export 동작과 선택 행 출력 기대가 충돌하지 않는지 별도로 확인한다.
- 실제 프린터 출력, 스캐너 입력, 고객 PC 드라이버/USB/COM/LAN 연결은 장비 검증 전까지 미확인 위험으로 기록한다.

## 예상 속도 개선

아래 수치는 현재 프로젝트처럼 작업 범위가 자주 바뀌고, 고객 실행 표면 검증이 중요한 Windows 로컬 프로젝트 기준의 보수적 추정이다.

| 작업 유형 | 단일 에이전트 대비 예상 시간 | 속도 개선 |
| --- | ---: | ---: |
| 1~2개 파일의 단순 수정 | 90~115% | -15~+10% |
| 원인 분석이 필요한 버그 수정 | 60~75% | 25~40% 빠름 |
| UI/UX 개선 + 브라우저 확인 | 65~80% | 20~35% 빠름 |
| 패키징/배포/검증 포함 작업 | 55~75% | 25~45% 빠름 |
| 요구사항이 불명확한 큰 기능 | 60~80% | 20~40% 빠름 |

실무 기준으로는 전체 평균을 25~35% 단축으로 잡는 것이 현실적이다. 10시간짜리 작업이면 약 6.5~7.5시간, 4시간짜리 작업이면 약 2.6~3.2시간 수준이다.

## 속도가 빨라지는 이유

- 진단 라운드에서 구현 전에 위험을 잡아 재작업을 줄인다.
- 해결안 토론에서 과한 리팩터링과 임시 구현을 걸러낸다.
- 구현과 검증 역할을 분리해 빠진 검증을 줄인다.
- 회의록이 남아 다음 작업자가 같은 맥락을 다시 찾는 시간을 줄인다.

## 느려지는 경우

- 한 파일만 고치는 작은 작업은 회의 오버헤드가 더 크다.
- 실제 외부 장비, 운영 서버, 계정 인증이 병목이면 AI 에이전트 수를 늘려도 시간이 크게 줄지 않는다.
- 여러 에이전트가 같은 파일을 수정하면 충돌 조정 때문에 느려진다.
